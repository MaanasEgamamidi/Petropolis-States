Linear path through the build — practice until this fits your timing.
  1. Main Menu → start game (Person 1 may still be speaking; Person 2 positions hands on controls).
  2. Character creation → choose appearance, enter a valid name, confirm → loads World.
  3. World → walk to pet shop (additive PetChoose) → pick dog appearance / name → return to World.
  4. Care & economy → show HUD / stats (hunger, health, happiness, energy); perform at least one care action (feed, play, rest, clean, or vet) so numbers move.
  5. Minigames / jobs → stand in a MinigameLauncherZone (hint: Press E / X to play) → play one short session — e.g. ReactionTime (three reaction trials), Pong (hits pay until a miss), or FlappyBird (beams cleared pay) — then return to World with an on-screen You earned $X style notification and higher cash.
  6. Supermarket NPC → open chat → negotiate a price → complete a purchase (shows AI + money + inventory).
  7. Bank NPC (short) → finalize a small loan with stated principal, interest %, and term — OR mention it verbally and show LoansPanelController / owed balance if live chat is too slow.
  8. Session report → stop play mode (Editor) or trigger quit flow so Session Reports/SessionReport#.html is generated → open the HTML file for judges.

If Wi‑Fi fails at NLC, say your backup plan out loud (PDF warns internet may be unreliable): e.g. show recorded clip, offline error path in chat, or pre-generated report — aligns with “Presentation Protocols” professionalism.

  • User Experience & Navigation — Menus, world navigation, chat UI, optional pause/instructions; on-screen prompts.
  • Input Validation — Name rules in character screen; loan bounds in GlobalData.TryOpenLoan; semantic checks in trackers / NPC prompts.
  • Functionality (topic) — Named pet, care actions, emotional/stat feedback, expenses, optional earning via minigames (topic: chores/tasks to earn pet-care funds), loans.
  • Data & Logic — Static session state, PlayerPrefs, lists of money snapshots for graphs, day-night driving economy events.
  • Presentable report — HTML export with charts, purchases, feedings, chat transcript.
  • Documentation — GameHelpContext.md (feature / help doc) → root README with Table of Contents (About through License) → Dependencies and libraries → Credits / attributions; all source in Git. Day–night, Starter Assets movement, and Bernie (store NPC) called out in spoken close.

Segment 0 — Setup (during official 3 min setup)

Clock: competition setup window (not scored as the 7 min)

On screen Laptop: Unity Editor or build fullscreen; second device optional for code PDF. Main Menu visible when judges are ready.
Person 1 (Silent during setup per guidelines.) Test audio comes from the device only — no external speakers in preliminary.

Segment 1 — Introduction

~0:00–0:55 (≈55 s)

On screen Title / Main Menu. Optional: brief splash or team slide for 5 s, then game. Person 2 does not play yet; Person 1 speaks to judges.
Person 1 “Good morning, judges. We’re Harshil Sharma, Maanas Egamamidi, and Dev Agarwal. We’re presenting Petropolis, a 3D life-simulation RPG built in Unity for the Build a Virtual Pet topic. Players name and customize themselves and their dog, care for it over time, and pay real costs — food, supplies, vet care — using an in-game economy. They can also earn money through minigames to cover those costs. We designed it as a modular program with clear data flow, validation, and a session report judges can analyze. I’ll hand the controls to [Person 2] for the live demo, while [Person 3] connects what you see to our code.”
Rubric Functionality / topic alignment — Opening states the FBLA prompt (pet + financial responsibility). Presentation Delivery — Clear, logical opening; all three members introduced; eye contact with judges.

Person 1 slides keyboard/controller to Person 2; Person 3 stands/sits where they can glance at code without blocking the game view.

Segment 2 — Character creation → World

~0:55–1:45 (≈50 s)

On screen Person 2: Main Menu → New/Start → Character screen. Cycle head/body options; type a valid player name; confirm. Scene loads into World. Avatar should match selections.
Person 2 (Short, functional narration.) “I’m choosing my look and name — now we’re in the open world.”
Person 3 “Customization writes to GlobalData.SaveChoice so the next scene reads one consistent player profile. We also mirror indices in PlayerPrefs for persistence. That separation — static session data plus disk prefs — is the kind of structure the rubric calls Data storage and Data & Logic.”
Rubric notes Topic — Customization ✓ Data storage — show variables with clear roles; mention prefs + static fields. Code Quality — point to meaningful API names like SaveChoice. Presentation — Person 3 speaks during action so judges hear code while seeing the result.

Segment 3 — Pet shop adoption

~1:45–2:35 (≈50 s)

On screen Person 2: Walk to pet shop trigger → PetChoose overlay → select dog variant / name → confirm → back to World with pet following or visible.
Person 2 “I’m adopting my dog and choosing how it looks.”
Person 3 “Adoption calls GlobalData.SavePetChoice, which clamps the skin index and fires OnPetConfirmed. The world scene reads that static state so art and UI stay in sync — that’s modular coupling: one source of truth for pet identity.”
Rubric notes Functionality — User names pet and chooses type/look. Modularity — event-driven updates. UX / Navigation — additive scene is a deliberate flow (world still loaded).

Segment 4 — Pet care, stats, cost of care

~2:35–3:15 (≈40 s) — keep care demo tight to leave room for minigames

On screen Person 2: Open pet status / HUD. Perform care: e.g. feed (costs money), play, rest, clean, or quick vet visit — show stat bars moving and balance decreasing. If day-night is visible, mention morning/evening in one line.
Person 2 “Hunger and happiness dropped over time — I’m feeding and playing to stabilize stats, and my cash is dropping when I buy care.”
Person 3 “Stats live on GlobalData — hunger, health, happiness, energy, cleanliness — updated by care actions and time. Purchases and feedings are logged into lists on SessionTracker for the report. That hits running totals and appropriate data structures for the topic.”
Rubric notes Topic — Feed, play, rest, clean, health check. Reactions — stats reflect treatment. Cost of care — visible money change. Data & Logic — centralized stat mutations; session logging.

Segment 5 — Minigames (earn pet-care money)

~3:15–3:55 (≈40 s)

On screen Person 2: From World, walk to a minigame job zone (on-screen hint such as Press E / X to play). Press interact to launch an additively loaded minigame scene — prefer ReactionTime for a fast demo (three reaction trials), or show Pong / FlappyBird if that zone is closer in your layout. Play until payout (reaction test finishes, or one quick game-over in Pong/Flappy). Judges should see the return to World and a notification that dollars were earned; cash in the HUD should increase.
Person 2 “I’m playing a quick minigame job to earn extra money before I go shopping for my pet.”
Person 3 “Zones use MinigameLauncherZone: when you’re inside the trigger and press E or the controller’s west face button, we call MinigameSession.StartSession with a scene name like ReactionTime, Pong, or FlappyBird under Assets/Scenes/Minigames/. MinigameSession additively loads that scene, freezes the World’s root GameObjects so cameras, audio, and input don’t conflict, then activates the minigame scene — the same additive pattern we use for PetChoose. Each game calls MinigameSession.AddPayout as you score: ReactionTimeGame pays from reaction speed, PongGameManager pays per successful hit until a miss, FlappyBirdGameManager pays per beam cleared. When the run ends, MinigameSession.EndSession rounds PendingEarnings and credits GlobalData.PlayerMoney, unloads the minigame, and unfreezes the World. That’s the prompt’s optional earning system — tasks to earn pet-care funds — implemented as clean, reusable session logic.”
Rubric notes Functionality / topic — “Optional: savings goals or earning systems (e.g., chores or tasks to earn pet care funds).” Modularity — launcher zone vs session manager vs individual minigame scripts in Petropolis.Minigames. UX — clear on-screen interact hint; return flow restores World in place. Data & Logic — single payout pipeline into the same balance that feeds purchases and reports.

Segment 6 — Supermarket: AI negotiation & purchase

~3:55–4:50 (≈55 s)

On screen Person 2: Enter supermarket, open NPC chat. Type one or two messages to haggle (e.g. lower price on dog food). Show finalized purchase and updated inventory / cash.
Person 2 “I’m negotiating in plain English — the shopkeeper just agreed to a final price.”
Person 3 “The NPC uses NpcOpenAiChatBridge to call OpenAiChatCompletionClient with the conversation history. If the API errors, the player sees an error string instead of a fake reply — that’s honest fallback behavior for unreliable conference Wi‑Fi. After each assistant message, ShopPurchaseTracker asks the model for strict JSON extraction of finalized items only; we only debit cash when the model confirms a completed sale. ChatManager strips hidden price/loan blocks from the visible transcript. Together that’s input validation on semantic level plus clean separation of concerns.”
Rubric notes UX — “intelligent feature such as interactive Q&A” — natural-language shop. Input validation — JSON shape, item names from inventory whitelist, guard rails in NPC docs. Modularity — bridge vs tracker vs chat UI. Documentation — cite OpenAI + Newtonsoft as external services/libraries.

Segment 7 — Bank loan (interest math)

~4:50–5:15 (≈25 s) — keep short; skip or narrate UI-only if behind schedule

On screen Person 2: Talk to bank officer OR open loans UI showing principal, APR, days left, amount owed. Prefer a completed in-chat loan if time allows.
Person 2 “I’m taking a short loan so we can show interest and repayment pressure.”
Person 3 “Negotiated loans are extracted by BankLoanTracker, then GlobalData.TryOpenLoan validates principal, interest rate, and term against min/max constants. Amount owed is Round(principal × (1 + interestRate)) — simple interest packaged as one payoff total. Each in-game day ticks down with LoanDayTicker; default triggers a fail state — that’s consequence-based financial literacy tied to the topic.”
Rubric notes Optional earning/budget systems — loans as extension. Data & Logic — bounded parameters, deterministic formula. Functionality — connects economy to pet stakes.

Segment 8 — Session HTML report

~5:15–5:55 (≈40 s)

On screen Person 2: Exit play (Editor) or quit to generate report. Open latest Session Reports/SessionReport#.html in a browser; scroll to money chart, stat graphs, purchase list, and chat excerpt.
Person 2 “Here’s everything we did — money over time, pet stats, and what I bought.”
Person 3 “SessionTracker samples money and pet stats on a schedule and on quit. ReportWriter.Generate writes UTF‑8 HTML with Chart.js: judges can analyze trends without re-running the game. That directly targets Program generates a presentable report at the ‘Exceeds’ level — error-free summaries for analysis.”
Rubric notes Report row — customizable analysis via charts and tables. Data storage — lists of snapshots / purchases / feedings. Tie back to Functionality — proves the virtual pet + economy story with evidence.

Segment 9 — Conclusion (Person 3 doc highlights → Person 1 close)

~5:50–6:50 (≈60 s) — adjust to finish before 7:00; trim Person 3 if behind schedule

On screen Optional: README open at Table of Contents; or a folder with GameContext/GameHelpContext.md + README printout; github.com/…/Petropolis-States (Git). Return to Main Menu or neutral desktop.
Person 3 “On documentation: our day–night pipeline is called out in the README Features and Technical Details—real-minute cycle, lighting, in-game time. Player movement is third person on Unity Starter Assets, with the full control table in GameHelpContext.md and in How to Play. Bernie—our AI supermarket owner—is a named, rules-driven character under NPC_Personalities/storeowner, not a generic shopkeeper, and that’s what keeps negotiation fair.”
Person 1 “We order documentation for judges like this: start with the feature document—Assets/GameContext/GameHelpContext.md—it powers Pause → Help. Then the README, which begins with a Table of Contents that labels every section—About through License, including Dependencies and libraries for all external tools and services, and Credits for attributions. All C# and project source are in Git with a public clone in the README.

To summarize the build: Petropolis meets the prompt with customization, care, stat feedback, spending, minigames to earn pet-care money, optional loans, AI-assisted shopping, and an HTML report—modular code and validation throughout. Thank you for your time — we’re happy to answer your questions.”
Rubric notes Documentation — feature doc, README ToC, externals, Git, attributions; Delivery — strong close. Protocols — no judge QR scans; ≤3 devices; materials not left behind.
